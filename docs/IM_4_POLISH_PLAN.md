### 1.2 代码中已核实的性能问题

数据层（按影响排序）：

1. **消息列表 N+1 查询**：`ImHomeVM.threads` 每次刷新对每个伙伴各读 40 条消息节点并解码 JSON；上游合并了整个 `settingsFlow`，任何设置写入（含每次启动的启动计数）都会触发全量重算。
2. **伙伴间聊天整表监听**：`PartnerChatDAO.observeAllMessages()` 无过滤地读全表，`observeSummaries()` 每次 O(会话 × 消息)，`observeApprovals()` 每个会话再订阅一遍整份快照。
3. **流式输出时整条时间线重建**：每个流式分片都让 `AgentThreadVM` 重新执行 `indexedSegments`（含 O(段²) 的过滤）和 `ThreadTimeline.build`（全量排序与分组），最多 12 段。
4. **缺索引**：`conversationentity` 没有任何索引（首页、目录、段戳查询都是全表扫描）；`message_node` 缺 `(conversation_id, node_index)`；`revision.author` 无索引；收藏表用 `LIKE 'node:'||?||':%'` 前缀匹配，用不上索引，且每次加载段都执行。
5. **全文索引每次保存都整段重建**：`MessageFtsManager.indexConversation` 删掉整段再全部重插（流式过程中不保存，只在保存时发生）。

启动路径：

6. `MiffanApp.onCreate` 主线程上做了：启动器图标组件同步（PackageManager IPC）、QuickJS 原生库加载、构造 `RelayConnectorUpdates`（连带构造 `WorkspaceRepository` 等一串对象）、`ModelCatalogRepository`、`UpdateChecker`；Koin 有两个 `createdAtStart` 单例。
7. `RouteActivity` 字段注入 `WorkspaceRepository`；每次回到前台都跑远程任务结果同步和更新检查。

界面层：

8. Markdown 在消息首次组合时同步解析（`MarkdownNew` 生成 HTML、`Markdown` 解析语法树），长消息滚动进入屏幕时卡顿。
9. 推理计时器每 50 ms 写一次状态；消息列表每行都新建日期格式化器；`ZoomableAsyncImage` 每次组合都新建图片请求；屏幕页的步骤时间线、伙伴 Tab、收藏页的列表计算没有缓存；电脑操作截图以原始分辨率解码。

## 4. 基线与目标

测量方法（W0 已交付，见 `docs/development/PERF_FIXTURE.md`）：`scripts/perf/run_bench.sh <serial>` 构建并安装独立包名的基准包
`me.ayuilos.miffan.app.bench`（调试签名，与正式版并存，脚本拒绝操作其他包），自动灌入测试数据并跑全套基准。
模拟器为软件渲染，帧数据只用于确认脚本可用；真机数据填在下表。

模拟器冷启动追踪（2026-11-08，`.bench` 包，3 次）：TTID 1.33 s、TTFD 2.86 s。`bindApplication` 533 ms 中 338 ms 是系统加载
dex/应用镜像；首帧后的几个长帧（218/340/456 ms）主要耗在 `postAndWait`，即等软件渲染的 RenderThread，是模拟器特有开销。
属于应用代码的：首次中文文字排版约 80 ms（含加载 CJK 字体）、首次组合 30–40 ms、Haze 模糊初始化约 15 ms。结论：启动剩余优化
以真机追踪为准，模拟器数据不作为依据。

## 6. 第二轮：流式回复的渲染（2026-11-10）

4.9.1 之后的一轮性能优化，范围是「伙伴正在回复时」这条路径。方法和第一轮不同：不跑 Macrobenchmark，直接在模拟器上用
`simpleperf` 对 `.bench` 包采样（2000 Hz，带调用栈），按线程和函数统计 CPU；配合 Perfetto trace 数重组次数。模拟器的帧率不可信，
但各线程的 CPU 时间和采样占比可以前后对比。场景：性能测试数据，主伙伴线程里发一条消息，假模型以 150 token/s 流式返回约 3000 token
的 Markdown（标题、列表、表格、代码、公式）。

### 6.1 采样发现的问题

| 位置 | 问题 | 基线占比 |
| --- | --- | --- |
| 界面（重组） | 两个静态 CompositionLocal 的值不断变化：回复的 `parts`（每个分片都变）和每次重组都新建的 `ThreadPartnerTransition`。静态 Local 变化时其下所有内容无条件重组，所以已写完的段落、表格单元格、代码块每个分片都重画；每敲一个字、每次开始滑动也会让所有可见消息重组 | 主线程 44% 在重组 |
| 界面（Markdown） | 每个分片整篇重新解析并生成全新的语法树；解析未完成又来新分片时结果被丢弃，长回复 + 快模型时画面会停在旧内容上 | 主线程 21% |

### 6.5 没做和待确认

- **标签切换**：每次切换都把整个标签页从头组合（真机 P99 73 ms）。让访问过的标签保持存活可以消除，但隐藏标签里的常驻动画（「我」页的大形象、工作中的光环）会继续跑帧，需要逐个停掉；涉及交互和耗电取舍，没有动。
- **分段高亮的已知局限**：还在流式输出、或超过 4096 字符的代码里，跨越 16 行分段边界的 Ruby heredoc、反斜杠续行（C 宏、Dockerfile `RUN`、properties）、Markdown setext 标题、C# 的原始字符串会缺颜色；写完且不超过 4096 字符后恢复为整段高亮。HTML 页面里的 `<script>` / `<style>` 用的语言是自动识别的：分段时按它在第一段里出现的那部分识别，之后的分段沿用这个结果，极少数情况下会和整段识别的结果不同。
- **Markdown 增量解析**：每个分片仍然对整篇文字跑一遍公式定界符预处理（`\(`、`\[` 的替换）；没有这些定界符时只是一次字符串查找，没有再改。
- **OpenAI 流解码**：每个分片解析两遍 JSON 并新建一个带随机 ID 的消息对象，属于上游代码，没有动。
- 后台循环审计（W1.8）粗查了 35 处循环：都是页面内的或分钟级的进程内定时器，没有发现需要处理的常驻轮询。
