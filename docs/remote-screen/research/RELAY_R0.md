# 中转 R0 验证报告

日期：2026-11-01（周日）18:30–19:30，北京时间晚高峰。方案见 [RELAY_PLAN.md](../RELAY_PLAN.md)。

代码：`relay/spike/`（Worker + Durable Object 中转、Go 工具），`workspace/src/test/.../RelaySpikeLiveTest.kt`（JSch over WebSocket）。测试中转部署在 `relay-dev.miffan.ayuilos.me`（Worker `miffan-relay-dev`，口令保护）。

## 1. 结论

1. **通路可行。** JSch → OkHttp WebSocket → Worker/Durable Object → Go connector → sshd 跑通了 SSH 登录、exec 和 SFTP（2 MiB 往返校验一致）。connector 只主动外连，电脑不开任何端口。
2. **Cloudflare 免费方案从国内用，延迟偏高但能用。** 手机和电脑都在国内时，每个包要出境两次。电信宽带晚高峰下，最好的组合往返约 450 ms，250 KB 截图约 0.9 s，吞吐 4–10 Mbps。适合"伙伴在外操作电脑"，看画面只能勉强（VNC 省流档），高性能模式不现实。这与"免费服务、不满意就自己部署"的定位相符。
3. **入口线路比对象位置更重要，而且要主动选。** 本域名默认被分到阿姆斯特丹；手动指定入口 IP 后，美西（洛杉矶、圣何塞）明显更好。新加坡 ICMP 最快，但晚高峰 TCP 很差。→ App 与 connector 需要"入口 IP 优选"（§4.2）。
4. **免费额度的瓶颈是 Durable Object 运行时长，而它只在有数据时才计算。** 空闲的 connector 和空闲的会话都会休眠，不计时长。→ 官方实例的配额应该按"活跃时长"算，不按流量算（§5）。
5. **Durable Object 固定在第一次创建时的位置附近**，需要由 connector 注册时带上位置提示（`locationHint`），并通过优选入口创建。

### 3.5 休眠与运行时长

同一对象（SJC），用"唤醒次数"计数（对象每次被重新构造计 1 次；每次查询统计本身也会唤醒 1 次）：

| 场景 | 时长 | 唤醒次数增量 | 解读 |
|---|---|---|---|
| connector 在线，无会话 | 2 min | +1 | 休眠 |
| 会话开着，只有 30 s 一次的文本 `ping`（运行时自动回复） | 3 min | +1 | 休眠，会话保持 |
| 每 60 s 一次数据 | 3 min | +3 | 每次数据唤醒一次 |
| 每 20 s 一次数据 | 2 min | +6 | 每次数据唤醒一次 |
| 每 5 s 一次数据 | 2 min | +0 | 一直醒着 |

对象在大约 10 s 无事件后休眠。全程 connector 没有重连，空闲会话没有被 Cloudflare 断开。

## 4. 对方案的影响

### 4.1 保活

- 经中转时，**连接保活一律用 WebSocket 文本 `ping`**（由运行时自动回复，不唤醒对象，也不计请求），间隔 30 s。
- 经中转时，JSch 的 `ServerAliveInterval` 关闭或设得很长：SSH 层的保活是加密数据，每次都会唤醒对象。
- App 不应在后台持续轮询电脑（例如每几秒一次状态查询），否则对象会一直醒着。

### 4.2 入口 IP 优选

- 默认 DNS 给的线路不是最好的，而且因运营商而异。
- 做法：中转在 `hello` 里不需要做任何事。App 和 connector 内置一组候选入口 IP（加上默认 DNS），启动时并行测 TLS 握手时间，选最快的，定期重测；TLS 的 SNI 仍是中转域名，证书校验不变。
- 候选 IP 只是"线路"，不影响安全：证书仍然校验中转域名，SSH 仍然校验主机密钥。
- 不同 zone 可用的 IP 不同（`1034`），候选列表由中转部署者提供（例如 `GET /v1/edges` 返回），官方和自部署都适用；VPS 部署返回空列表即可。
- 风险：依赖 Cloudflare 的路由现状，可能随时变化；所以必须保留默认 DNS 作为候选之一，并持续重测。

### 4.3 对象位置

- 对象位置由 connector 第一次注册决定。connector 应先做入口优选，再带 `locationHint` 注册。
- 提示值根据优选出的入口选择（美西入口 → `wnam`）。
- 已创建的对象位置不能更改；如果长期不理想，可以换一个 hostId 重新注册（需要重新配对 → R1 要支持"更换中转身份"的流程）。

## 5. 免费额度测算

Cloudflare 免费方案（2026-11 文档）：Durable Object 每天 100,000 次请求、13,000 GB·s 运行时长；收到的 WebSocket 消息按 20 条计 1 次请求，发出的消息和自动回复的 `ping` 不计；每天 UTC 0 点（北京时间 8 点）重置。Workers 自身每天 100,000 次请求，每次 WebSocket 连接计 1 次。

- **运行时长**：对象按 128 MB 计费，13,000 GB·s ≈ **每天约 28 小时的"对象醒着"时间**，所有用户共用。
- **请求数**：大流量时每条消息接近 64 KB，1 GB ≈ 16,000 条 ≈ 800 次请求，不是瓶颈。建会话会产生几次 Workers 请求（客户端连接、connector 数据连接、统计查询），每天 10 万次足够数千次会话。
- **按场景估算的对象活跃时间**：
  - 伙伴操作电脑：只在操作时醒着。一个 10 分钟、动作间隔几秒的任务约 10 分钟。
  - 看画面：持续醒着，看多久算多久。
  - 电脑在线待命、会话空闲：几乎为 0。

→ 官方实例的策略应以**每台电脑每天的活跃分钟数**为主要配额（例如每天 30 分钟），并给全局每天的活跃时长设预算；流量配额只作为次要限制。VPS 部署的成本是流量，所以两种配额都要支持（这是对 RELAY_PLAN §5.1 的修正）。

具体额度需要在 Cloudflare 后台核对一次真实的运行时长（Durable Objects → 指标）后再定。
